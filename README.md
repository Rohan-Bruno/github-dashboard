# GitHub Issues Dashboard (single repo)

Static, buildless, framework-free. A Node script pulls issue data from the GitHub REST API into
`data.json`; `index.html` reads it and renders charts with Chart.js from a CDN.

```
fetch_data.mjs              # data fetcher (Node 20+, zero dependencies)
.env                        # local PAT + config, git-ignored, never committed
serve.mjs                   # static server, Node built-ins only
index.html                  # the whole dashboard
data.json                   # committed SAMPLE, overwritten by the fetcher
.github/workflows/refresh.yml
```

## 1. Create the PAT and repo secret

The Actions-provided `GITHUB_TOKEN` is capped at **1,000 REST requests/hr** per repository, which is
**not enough for a full-history pull** (a repo with a few thousand issues + comments + events blows
past it). A user PAT gets **5,000/hr**.

1. GitHub → Settings → Developer settings → Personal access tokens.
   - Fine-grained: select the repo, `Issues: read-only` + `Metadata: read-only`.
   - Classic: `public_repo` for a public repo, `repo` for a private one.
2. Repo → Settings → Secrets and variables → Actions → New repository secret,
   name it **`GH_PAT`**, paste the token.
3. For local runs, put the same token in `.env` as `GITHUB_TOKEN` (see below). `.env` is git-ignored
   and CI never reads it — Actions gets the token from the `GH_PAT` secret.

The workflow passes it in as `GITHUB_TOKEN`.

## 2. Configure

All config is env/constants at the top of `fetch_data.mjs`, mirrored in `refresh.yml`'s `env:` block:

| var | default | meaning |
|---|---|---|
| `OWNER` / `REPO` | `usebruno`/`bruno` | the single repo to pull |
| `INTERNAL` | *(empty)* | comma-separated internal logins, matched **case-insensitively** (GitHub logins are); drives the internal-only toggles and the unanswered rule |
| `GITHUB_TOKEN` | `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` | PAT. Unauthenticated is 60 req/hr — it will not finish |
| `DROP_BOTS` | `1` | drop logins matching `/\[bot\]$/i`; set `0` to keep them |
| `MAX_CLOSED_KEPT` | `1500` | cap on closed issues kept **in the table**. Counts stay exact |
| `SIM_THRESHOLD` | `0.75` | title token-set Jaccard for near-duplicate clustering |
| `STALE_DAYS` | `60` | an open issue with no update in this long counts as stale |
| `MAX_RATE_WAIT_MS` | `300000` | if the rate limit resets further out than this, fail fast with a "set a PAT" message instead of sleeping |

Every config value and every metric definition is printed at the start of each run.

## 3. Run locally

Put the PAT and the repo config in **`.env`** once (it is git-ignored — see `.gitignore`):

```
GITHUB_TOKEN=ghp_xxx
OWNER=usebruno
REPO=bruno
INTERNAL=login1,login2
```

`fetch_data.mjs` loads it via `process.loadEnvFile()` (Node built-in, no `dotenv` package), resolved
relative to the script, so it works from any working directory. **Real environment variables win over
the file**, so CI secrets and a one-off `OWNER=other node fetch_data.mjs` still override it.

```bash
node fetch_data.mjs            # reads .env
node serve.mjs                 # then open http://localhost:8731
```

`node serve.mjs 9000` picks a different port. No dependencies and nothing to install — it is
`node:http` plus `readFile`.

The token is never printed: the config banner shows only `token: set (N chars)`.

`node fetch_data.mjs --self-test` runs the title-normalisation / clustering / pagination asserts
without touching the network.

The committed `data.json` is a sample **generated by running this fetcher over a stubbed API**, so it
always matches the real schema and the real metric math — including the reopen/reclose case (issue 98
is credited to its second closer, not its first).

Opening `index.html` straight off the filesystem works too — `fetch('./data.json')` is blocked on
`file://`, so the page falls back to a tiny built-in sample and says `source: fallback` in the header.

## 4. Refresh cadence and deployment

`.github/workflows/refresh.yml` runs **daily at 04:17 UTC** (`cron: '17 4 * * *'`) plus
`workflow_dispatch` for a manual run. Change the cron line to change the cadence.

A full run costs ~1,330 API requests (~27% of one hour's 5,000 PAT budget) and ~13 minutes, so even
hourly (`0 * * * *`) stays inside the rate limit. Actions minutes and artifact storage are free on
public repos; on a private repo hourly would run ~9,400 min/month against a 2,000-minute free tier.
Note that a higher frequency does **not** improve accuracy — each run is an independent snapshot,
and the 30,000-event cap on close attribution is the same at any cadence.

Deployment is a single toggle, `DEPLOY_TARGET` in the workflow's `env:` block:

- **`artifact` (default)** — uploads `site/` as a workflow artifact, 14-day retention.
  Download → unzip → open `index.html`.
  **Artifact visibility follows repository visibility.** In a private repo only collaborators can
  download it. In a **public** repo anyone can, from the Actions tab — the artifact is not private.
  If the per-person metrics should stay internal, put this dashboard in a **private** repo. It can
  still pull from a public source repo: the PAT only needs public read access.
- **`pages`** — publishes to GitHub Pages. Set `DEPLOY_TARGET: pages`, uncomment the `permissions`
  block and the two `pages-*` steps, and enable Settings → Pages → Source: GitHub Actions.

> **Warning about publishing.** This dashboard is per-person productivity data: who closed which
> tickets, who comments how much, who is carrying the assignee load. That is exactly the sort of
> thing that gets read as a leaderboard. On a **public** repo, both Pages *and* workflow artifacts
> are readable by anyone — picking `artifact` over `pages` does not keep it internal. The only way
> to keep it internal is a private repo for the dashboard. Whichever you choose, tell the team first.

## Metric definitions

Named constants in the `DEF` object at the top of `fetch_data.mjs`, printed on every run and copied
into `data.json` under `meta.definitions`, so the dashboard always shows what it actually measured.

| metric | definition |
|---|---|
| **unanswered** | open issue with **zero comments from an `INTERNAL` login** — community-only replies still count as unanswered. With `INTERNAL` unset there is nobody to be internal, so it degrades to zero comments overall |
| **assigned** | issues assigned to a login, **open and closed**, drawn as grouped open/closed bars. An issue with N assignees counts once for each of them, so the per-assignee totals sum to more than the issue count |
| **self_closed** (primary) | issues whose close-event actor **equals the issue author**, counted per author |
| **authored_closed** (secondary) | closed issues grouped by their author, **regardless of who closed them** |
| **closed_by_them** | close actions attributed to whoever closed the issue |
| **duplicates** | (a) label `duplicate`, or `state_reason` of `duplicate`/`not_planned`; (b) normalized-title token-set Jaccard ≥ `SIM_THRESHOLD` (0.75) |
| **stale** | open issue with no update in `STALE_DAYS` days |
| **open_bugs** | open issue with any label matching `/bug/i` |

## Caveats

**Pull requests are excluded.** `GET /issues` returns PRs too; any item with a `pull_request` field
is dropped. `meta.counts.prs_excluded` reports how many.

**PR comments are dropped (this is the choice we made).** `GET /issues/comments` includes comments
on PRs, because GitHub treats PRs as issues. Each comment's `issue_url` is resolved to an issue
number and kept only if that number is in the set of known non-PR issues. So **comment counts are
issue-conversation only** — a reviewer who lives in PRs will look quiet here. The run log prints how
many comments were dropped.

**Close events are deduped to the most recent closer per issue (this is the choice we made).**
`GET /issues/events` records close *actions*: an issue reopened and reclosed produces several. We
keep only the latest close event per issue, so `closed_by_them` and `self_closed` are counts of
**unique issues**, not of close actions. If you want action counts instead, drop the
`if (!prev || e.created_at > prev.at)` guard in `fetch_data.mjs`.

**One duplicate finding per issue.** An issue carrying both the `duplicate` label and a duplicate
`state_reason` is reported once, as `label`, with the `state_reason` in `detail` — it is not counted twice.

**Duplicate detection is heuristic and over-matches.** Jaccard on title tokens has no idea what the
issues are about; "crash on save" and "crash on export" can cluster. The UI says so. The threshold is
`0.75` — tight enough that titles must share most of their meaningful words. Lower it toward `0.6`
for more recall and noticeably more false clusters. Clustering runs over the exported issues (all open plus
the most recent `MAX_CLOSED_KEPT` closed), not the full closed history.

**Counts vs table.** All open issues are exported. Closed issues are capped at `MAX_CLOSED_KEPT`
(most recently closed first) for the table, but `summary.open` / `summary.closed` and every
per-person aggregate are computed over the **full** paginated result, so they are exact.

**The events endpoint does not go back forever.** GitHub caps repository issue-event history, so
very old close attributions may be missing. Issue and comment history are complete.

**Filter scope in the UI.** The state/label/assignee/internal filters recompute the totals chart, the
KPI "in current filter" tile, the issue table, and the per-assignee chart. Comments-per-person and
closed-by-author come from the whole-history `people` aggregates and respond only to the
internal-only toggle — each card says which it is.

```json
  "summary": { "open": 0, "closed": 0, "unanswered": 0, "open_bugs": 0, "stale": 0 },
  "issues": [ { "number":0,"title":"","state":"","labels":[],"author":"","assignees":[],"comments":0,
                "created_at":"","updated_at":"","closed_at":"","state_reason":null,"closed_by":null,"url":"" } ],
  "people": [ { "login":"","internal":false,"assigned_total":0,"assigned_open":0,"comments":0,
                "closed_by_them":0,"self_closed":0,"authored":0,"authored_closed":0 } ],
  "duplicates": [ { "reason":"label|state_reason|title-similarity","members":[ {"number":0,"title":"","state":""} ] } ] }
```
